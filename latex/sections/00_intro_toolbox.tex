\section{Introduction}

This report is our submission for the FCA Team Lab ``The Speed of Numbers,'' where we investigate how different ways of representing numbers (integers, floats, fixed-point) affect execution speed on real hardware.

We are measuring latency on the ESP32 because it is a real, modern microcontroller (dual-core Xtensa LX6 @ 240\,MHz) with a hardware floating-point unit, and because \emph{predicting} performance from source code alone is unreliable --- only measuring on the actual board tells us the truth.

A number can be stored as an integer, a float, or a custom fixed-point format, and each choice has a different cost in CPU cycles and a different tradeoff in accuracy. This report measures those costs directly instead of assuming them.

\subsection{Platform}
All experiments run on an \textbf{ESP32-WROOM-32} board (dual-core 32-bit Xtensa LX6). Clock frequency is confirmed at $240\,\text{MHz}$ via \texttt{getCpuFrequencyMhz()} before each run.

\section{Toolbox Foundations}
Short answers to the five foundational questions from the assignment brief.

\begin{enumerate}[leftmargin=1.8em, itemsep=6pt]
    \item \textbf{How long is one clock cycle at 240\,MHz?}
    \begin{equation}
        T_{\text{clk}} = \frac{1}{240 \times 10^6\,\text{Hz}} \approx 4.17\,\text{ns}
    \end{equation}

    \item \textbf{If you time just one addition, what are you really measuring?}
    Mostly the overhead of reading the cycle counter itself, not the addition. \textit{[Pending: exact overhead split depends on Experiment 1 measurements.]} \\
    \textbf{Fix:} amortize by timing $N$ unrolled operations and dividing by $N$.

    \item \textbf{How do you find out what the loop itself costs?}
    Run an empty loop (same shape, no payload) and record its cycle count as the baseline $C_{\text{base}}$. Subtract it from the payload measurement:
    \begin{equation}
        C_{\text{op}} = \frac{C_{\text{total}} - C_{\text{base}}}{N}
    \end{equation}

    \item \textbf{Average, median, or minimum — which do you report?}
    We report the \textbf{minimum} (closest to the true hardware cost, least affected by RTOS jitter) alongside the \textbf{median} (typical case, filters outliers).

    \item \textbf{How do you stop the compiler from deleting or pre-computing your benchmark?}
    Declare operands \texttt{volatile}, or use an inline-assembly clobber (\texttt{asm volatile("" : "+r"(x))}) so GCC cannot fold or eliminate the computation.
\end{enumerate}
